안내서 1 · 증거 운영

높은 점수와 실제 출시 가능은 같은 말이 아닙니다.

성능 점수 하나가 100이어도 약관, 데이터 삭제, 실제 기기, 문의 대응이 비어 있으면 제품은 출시 준비가 끝난 것이 아닙니다. 준비도는 숫자가 아니라 “누가, 언제, 무엇으로 확인했는가”를 다시 설명할 수 있는 상태입니다.

갱신일 2026-08-31 · Readiness Hub core v2.1 기준

1. 증거를 다섯 종류로 나눕니다

종류예말할 수 있는 범위
자동 검사성능, HTTPS, 파일 존재그 검사 환경에서 측정됐다고만 말합니다.
브라우저 검사360px 가로 넘침, 키보드 이동해당 브라우저와 화면 조건의 결과입니다.
실제 기기Android 설치, 터치, 오프라인기기 모델·운영체제·날짜가 있는 경우만 인정합니다.
운영자 확인문의 수신, 환불, 장애 대응실제로 책임질 사람이 확인한 사실입니다.
외부 근거공식 정책, 계약, 공개 상태출처와 확인일이 있어야 합니다.

2. 확인일과 만료를 함께 적습니다

증거는 한 번 얻었다고 영원히 유효하지 않습니다. 앱스토어 정책, 개인정보 문서, 의존성, 성능은 시간이 지나면 달라집니다. 항목마다 확인일과 권장 재검사 주기를 기록하면 점수를 지우지 않고도 “갱신 필요”를 표시할 수 있습니다. 이렇게 하면 오래된 증거가 현재 사실처럼 보이는 문제를 피할 수 있습니다.

3. 필수 조건은 평균점수보다 먼저 봅니다

평균이 높아도 계정 삭제, 개인정보 고지, 실제 결제 총액, 치명적 장애 복구처럼 반드시 넘어야 하는 조건이 실패하면 출시 판정은 보류됩니다. Readiness Hub는 이런 항목을 필수 통과 조건으로 분리합니다. 사용자는 실패한 조건의 이유와 해결 방법, 필요한 증거를 먼저 보고 작업 순서를 정합니다.

4. 부족한 점을 작업으로 닫습니다

  1. 부족한 점을 발견하고 영향도를 적습니다.
  2. 담당자와 기한 또는 명시적인 차단 이유를 남깁니다.
  3. 수정 내용과 원본 근거를 연결합니다.
  4. 같은 조건으로 다시 검사합니다.
  5. 전후 결과와 완료 조건을 함께 보존합니다.
하지 말아야 할 일: 미확인을 0점과 섞기, 자동 검사를 실기기라고 부르기, 법률 검토 없이 준수 인증이라고 쓰기, 비교 자료가 부족한데 정밀 순위를 만드는 일입니다.

5. 최소 실행표

오늘 시작한다면 제품 이름·공개 주소·지원 플랫폼을 적고, 핵심 사용자 흐름 하나를 끝까지 실행해 봅니다. 그 흐름에 필요한 정책·저장·오류·접근성·복구 증거를 모읍니다. 확인하지 못한 항목은 숨기지 않고 미확인으로 남깁니다. 다음에는 영향도가 가장 큰 미확인 하나를 선택해 실제 증거로 바꿉니다.
