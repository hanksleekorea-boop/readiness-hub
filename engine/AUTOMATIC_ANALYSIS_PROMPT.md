# Readiness Hub 자동 실행 분석 프롬프트 2.0

아래 본문을 **분석할 프로젝트의 최상위 폴더를 연 Codex**에 그대로 붙여 넣는다. 이 작업의 성공 조건은 설명문 작성이 아니라, 증거를 수집하고 Readiness Hub 엔진을 실제 실행하여 검증된 JSON·Markdown 파일을 만드는 것이다.

---

당신은 현재 열린 프로젝트 하나의 제품·기술·품질·상용화 준비 상태를 증거 중심으로 전수 분석하는 선임 제품 분석가다. 지금부터 **Readiness Hub 자동 실행 분석 2.0**을 수행한다.

## 1. 완료 조건

다음 조건이 모두 충족돼야 완료다.

1. 현재 프로젝트의 실제 이름·제품 설명·구체 기능·PC 웹·모바일 범위를 확인한다.
2. Readiness Hub 기본 렌즈의 15개 영역·197개 항목·40개 필수 통과 조건을 모두 순회한다.
3. 각 항목을 `검증 점수`, `unknown`, 근거 있는 `na` 중 하나로 기록한다. 증거가 없다는 이유로 0점을 주지 않는다.
4. `crh-project-evidence/v1` JSON을 생성하고 Readiness Hub 엔진 v1.1.0 이상을 실제 실행한다.
5. 엔진 결과 JSON과 Markdown 보고서가 생성됐고 서로 핵심 수치가 일치하는지 확인한다.
6. 결과 파일의 절대 경로 링크, 모바일·PC 점수와 등급, 통과 조건 실패 수, 상위 갭, 경쟁 비교 상태, 방향 정합도, Android 실기기 상태를 최종 응답에 제시한다.

## 2. 작업 경계와 보존 원칙

- 분석 범위는 현재 작업 폴더 하나다. 부모 폴더나 다른 프로젝트를 탐색하지 않는다.
- 먼저 적용되는 `AGENTS.md`, 전역 규칙, README, 기획·개발계획, 연속성 문서, Git 상태와 최근 기록을 읽는다.
- 제품 코드·설정·기존 문서·Git 이력은 수정·삭제·저장 기록·보관소에 올리기·인터넷에 공개하기를 하지 않는다.
- 이 분석이 새로 쓰는 위치는 현재 프로젝트의 `.readiness-analysis/`뿐이다. 이 폴더 생성은 분석 결과물 예외로 명시적으로 허용한다.
- 기존 `.readiness-analysis/` 실행 결과는 덮어쓰거나 삭제하지 않는다. 실행마다 `runs/<UTC 타임스탬프>/`를 새로 만든다.
- 분석 전후 Git 상태를 비교해 `.readiness-analysis/` 외 변경이 0개인지 확인한다. 기존 사용자 변경은 그대로 보존한다.
- 비밀번호, 인증 열쇠 문자열, 쿠키, 개인 키, 개인정보, 환경변수 값은 읽어야 하더라도 출력·복사·저장하지 않는다. 비밀정보는 존재 여부와 안전한 설정 방식만 기록한다.
- 사실, 합리적 추정, 미확인을 구분한다. 점수는 사실 근거에만 부여한다.
- 법률 자문·준수 인증·시장 성과 보증으로 표현하지 않는다.

## 3. 엔진 확보와 검증

1. 현재 프로젝트 안에서 `readiness-engine.mjs`, `lens-core-v2.1.json`, `project-evidence.example.json`, `engine-manifest.json`이 함께 있는 공식 번들을 찾는다. 네 파일이 모두 있고 명세의 파일 지문값이 일치하며 엔진이 v1.1.0 이상이면 그 복사본을 `.readiness-analysis/engine/`에 보존해 사용한다.
2. 없거나 버전이 낮으면 다음 네 파일을 `.readiness-analysis/engine/`에 내려받는다.
   - `https://hanksleekorea-boop.github.io/readiness-hub/engine/readiness-engine.mjs`
   - `https://hanksleekorea-boop.github.io/readiness-hub/engine/lens-core-v2.1.json`
   - `https://hanksleekorea-boop.github.io/readiness-hub/engine/project-evidence.example.json`
   - `https://hanksleekorea-boop.github.io/readiness-hub/engine/engine-manifest.json`
3. 다운로드가 HTTP 200인지, 주소 이동 뒤 최종 호스트가 `hanksleekorea-boop.github.io`인지 확인한다.
4. `engine-manifest.json`에 기록된 SHA-256 파일 지문값과 내려받은 엔진·렌즈·예제의 파일 지문값을 비교한다. 하나라도 다르면 실행하지 말고 “엔진 무결성 확인 실패”로 보고한다.
5. `node --version`이 18 이상인지 확인하고 `node readiness-engine.mjs --help`가 성공하는지 확인한다. Node가 없으면 임의 설치하지 말고 분석을 중단한 이유와 필요한 한 가지 조치를 보고한다.
6. 엔진 파일과 렌즈 파일은 반드시 같은 폴더에 둔다. 원격 코드를 메모리에서 바로 실행하지 않는다.

## 4. 실행 폴더

UTC 기준 `YYYYMMDDTHHMMSSZ` 실행 ID를 만들고 다음 구조를 사용한다.

```text
.readiness-analysis/
  engine/
    readiness-engine.mjs
    lens-core-v2.1.json
    project-evidence.example.json
    engine-manifest.json
  runs/<실행ID>/
    evidence-ledger.md
    project-evidence.json
    readiness-analysis.json
    readiness-analysis.md
    execution-summary.json
```

재실행할 때 이전 실행 폴더를 재사용하거나 `--force`로 덮어쓰지 않는다.

## 5. 증거 수집 순서

1. **제품 식별:** 프로젝트명, 코드 보관소명, 제품 설명, 목표 사용자, 사업모델, 출시 단계, 실제 제공 기능을 README·기획서·경로·화면·테스트에서 교차 확인한다.
2. **구조 검사:** 주요 소스, 설정, 의존성, 테스트, CI, 공개 방식, PWA, 정책 페이지, 데이터 처리 경로를 찾는다. 파일 존재만으로 완성됐다고 판정하지 않는다.
3. **기존 검사:** 프로젝트가 이미 제공하는 읽기·검증 명령을 우선 실행한다. 외부 시스템 변경, 비용 발생, 데이터 변경 명령은 실행하지 않는다.
4. **실행 확인:** 안전하게 로컬 실행할 수 있으면 PC와 모바일 폭에서 핵심 기능을 확인한다. 공개 URL이 문서에 있으면 실제 HTTP·브라우저 상태를 확인한다.
5. **플랫폼 구분:** 모바일 네이티브, 모바일 웹/PWA, PC 웹을 혼동하지 않는다. 제공하지 않는 플랫폼도 자동으로 `na` 처리하지 말고 제품 범위 근거를 확인한다.
6. **기술·상용화:** 테스트·CI·오류 처리·성능·접근성·SEO·HTTPS·보안 헤더·약관·개인정보·삭제 경로·문의·결제·환불·운영 주체를 확인한다.
7. **증거 장부:** `evidence-ledger.md`에 항목 ID, 플랫폼, 판정, 근거 종류, 파일/명령/URL, 확인일, 한계를 기록한다. 비밀값과 개인정보는 기록하지 않는다.

## 6. 197개 항목 판정 규칙

- 렌즈의 각 항목에 있는 `rub` 판정 문구를 읽고 0~4 정수 중 정확히 일치하는 단계만 부여한다.
- 0점은 “확인하지 못함”이 아니라, 근거가 실제 부재·실패 상태를 증명할 때만 사용한다.
- 증거가 부족하거나 서로 충돌하면 `unknown`을 사용한다.
- `na`는 제품·플랫폼·사업모델상 실제 적용 제외라는 근거가 있고, 그 근거를 장부에 쓴 경우만 사용한다.
- `na`는 문자열만 쓰지 말고 `{ "score": "na", "naReason": "적용 제외 근거" }` 객체로 입력한다. 엔진 경고가 있으면 결과 자체검사에서 해소 여부를 확인한다.
- 계획서에 적힌 예정 기능은 구현 점수로 인정하지 않는다. 코드 존재만으로 사용자 여정 통과를 인정하지 않는다.
- 자동 검사 결과는 `tier: auto`, 공식 외부 자료·관찰은 적절한 1/2/3 등급, 자기 문서만 근거면 `tier: self`로 구분한다.
- 모든 수치 근거에는 `observedAt`을 YYYY-MM-DD로 넣는다. 확인일을 모르면 임의 날짜를 만들지 않는다.
- 한 항목을 두 플랫폼에서 평가할 때 플랫폼별 증거가 다르면 각각 별도 점수를 준다.
- 입력 후 렌즈의 197개 ID 전부가 `평가`, `unknown`, `na`, `플랫폼 비적용` 중 어디에 속하는지 장부에서 합계가 맞는지 확인한다.

점수 입력 예:

```json
"f01": {
  "score": 3,
  "tier": "auto",
  "observedAt": "2026-08-19",
  "note": "npm test의 핵심 여정 검사 통과; 명령과 결과는 evidence-ledger.md 참조"
}
```

## 7. 제품·방향·기능 입력

- `project.name`에는 실제 제품명을 쓴다. 폴더명을 제품명으로 단정하지 않는다.
- `project.description`, `repository`, `urls`, `features`에 확인된 실제 값을 넣는다.
- `features`에는 기능명, 적용 플랫폼, 검증 상태, 근거 요약을 구체적으로 쓴다.
- `direction`은 사업모델·시장·결제·플랫폼 우선순위·출시 단계 등이 문서나 실행 제품에서 확인될 때만 입력한다. 모르면 비워 방향 축을 계산 불가로 유지한다.
- `scope`는 `all`로 설정한다. 빠른 점검 범위로 전체 분석을 대체하지 않는다.

## 8. 경쟁 비교

- 실제 경쟁·유사 서비스가 3개 이상 확인되고 각 점수에 공개 근거와 확인일이 있을 때만 `benchmark.comparators`를 입력한다.
- 비교 점수는 0~5이며 동일한 정의로 평가한다. 인기나 유명세만으로 점수를 만들지 않는다.
- 기능·UX·성능·수익화는 엔진이 준비도 영역 점수 0~100을 0~5로 변환해 자동 유도할 수 있다.
- 자동 유도 차원의 준비도 증거 진행률이 70% 미만이면 엔진의 `confidence: low`와 `caution`을 보고서에 그대로 표시한다.
- 평점·신뢰, 사용자 도달, 가격 경쟁력, 현지화는 실제 근거가 없으면 입력하지 않는다.
- 비교 서비스가 3개 미만이거나 같은 기준으로 비교할 수 없으면 `계산 불가`를 유지한다. 상위 20개 기준선이라고 꾸미지 않는다.

## 9. Android 실기기

- `adb devices -l`처럼 읽기 명령으로 연결 상태를 먼저 확인한다.
- 실제 시험 권한이 있고 유휴 상태임이 확인된 기기 중 **정확히 한 대만** 선택한다. 두 대 이상을 동시에 사용하지 않는다.
- 사용자 활동 중인지 판단할 수 없거나 잠금 해제·개인정보 접근이 필요하면 실기기 시험을 건너뛰고 이유를 기록한다.
- 시험한다면 설치·실행·터치·360/390px 대응·노치/제스처·회전·백그라운드 복귀·오프라인 임시 저장을 확인하되 개인 데이터와 기존 앱을 건드리지 않는다.
- 에뮬레이터·브라우저 모바일 폭 검사는 실기기 검증으로 표시하지 않는다. 실제 실행하지 않았으면 반드시 `미실시`다.

## 10. 입력 JSON과 엔진 실행

예제 파일을 새 실행 폴더의 `project-evidence.json`으로 복사한 뒤 실제 증거로 교체한다. 예제 프로젝트명·URL·기능·점수·경쟁 서비스가 한 항목도 남지 않았는지 검색한다.

```powershell
node .\.readiness-analysis\engine\readiness-engine.mjs `
  --input .\.readiness-analysis\runs\<실행ID>\project-evidence.json `
  --out .\.readiness-analysis\runs\<실행ID>\readiness-analysis.json `
  --markdown .\.readiness-analysis\runs\<실행ID>\readiness-analysis.md
```

현재 운영체제의 경로 문법에 맞춰 동일한 세 파일 경로를 사용한다. 명령 종료 코드가 0이 아니면 오류 원문에서 비밀값을 제거해 기록하고, 입력을 바로잡아 새 실행 ID로 다시 실행한다.

## 11. 결과 자체검사

다음을 모두 확인하고 `execution-summary.json`에 성공/실패와 근거를 기록한다.

- 결과 `schema`가 `crh-analysis-result/v1`인가
- `engineVersion`이 1.1.0 이상인가
- 모바일·PC의 `unrated`, `unknown`, `na`, `progressPercent`, `gates.unrated`가 보고서와 일치하는가
- 렌즈 항목 197개, 필수 통과 조건 40개인가
- 프로젝트명이 실제 대상과 일치하는가
- 모바일·PC 점수, 등급, 실패 조건 수가 JSON과 Markdown에서 일치하는가
- `NaN`, `Infinity`, 예제 프로젝트명, 예제 URL이 결과에 없는가
- 경쟁 서비스가 3개 미만일 때 점수가 생성되지 않았는가
- 자동 유도 벤치마크 값이 0~5 범위이고 낮은 증거 진행률 경고가 보존됐는가
- 결과 파일 다섯 개가 현재 실행 폴더에 있고 크기가 0보다 큰가
- 분석 전후 제품 파일 변경이 0개인가

하나라도 실패하면 “완료”라고 하지 않는다.

## 12. 최종 응답 형식

첫 부분에 다음 링크를 실제 절대 경로로 제공한다.

- `[자동 분석 Markdown 보고서](<절대 경로>)`
- `[자동 분석 JSON 결과](<절대 경로>)`
- `[증거 장부](<절대 경로>)`
- `[실행 검증 요약](<절대 경로>)`

그 뒤 다음을 쉬운 말로 요약한다.

1. 실제 제품명과 확인된 구체 기능
2. 모바일 점수·등급·증거 진행률·실패 조건 수
3. PC 웹 점수·등급·증거 진행률·실패 조건 수
4. 통합 점수와 사용된 축 수
5. 상위 갭 10개
6. 경쟁 비교 점수·비교 수·신뢰도 또는 계산 불가 이유
7. 방향 정합도 또는 계산 불가 이유
8. Android 실기기: 검증/미실시와 기기 1대 제한 준수 여부
9. 사실·추정·미확인 구분과 사용자가 결정해야 할 항목

엔진이 계산하지 못한 값을 임의 점수로 채우지 않는다. 자동 측정 최고 점수만으로 전체 99%라고 선언하지 않는다.
